RL-Kernel：让强化学习的训练与推理真正执行同一个策略

RL-Kernel 是面向大语言模型强化学习后训练的基础设施，关注 PPO、GRPO 等流程中的训练—推理数值一致性，以及 GPU 算子的显存和计算效率。

本笔记依据提供的项目解读整理，实验数字和支持范围沿用该材料，未独立核验当前版本。

它研究的问题很具体：同一个模型、同一组权重、同一个 token，在推理引擎和训练引擎中算出的 log probability，为什么可能不同？这种差异又会怎样影响 RL 更新？

相同权重只是相同策略的一个前提。输入、缓存、概率定义和数值执行路径，也需要保持一致。

1. 为什么 log probability 不一致会影响 RL

典型的大模型 RL 流程中，推理引擎负责生成 response，训练引擎负责重新计算概率、构造损失和更新权重。例如：

vLLM 生成轨迹并记录 logprob → Megatron-LM 计算训练 logprob → PPO/GRPO 更新 → 同步权重。

对状态 sts_tst​ 和已采样 token ata_tat​，策略概率比可以写成：

rt(θ)=exp⁡(log⁡πθ(at∣st)−log⁡πrollout(at∣st)). r_t(\theta) =\exp\left( \log\pi_\theta(a_t\mid s_t) -\log\pi_{\mathrm{rollout}}(a_t\mid s_t) \right). rt​(θ)=exp(logπθ​(at​∣st​)−logπrollout​(at​∣st​)).

如果权重尚未更新，两个引擎使用相同输入与相同概率定义，理想情况下应有 rt=1r_t=1rt​=1。

例如，两边分别计算出：

log⁡πrollout=−1.20,log⁡πtrain=−1.18, \log\pi_{\mathrm{rollout}}=-1.20,\qquad \log\pi_{\mathrm{train}}=-1.18, logπrollout​=−1.20,logπtrain​=−1.18,

则：

rt=e0.02≈1.0202. r_t=e^{0.02}\approx1.0202. rt​=e0.02≈1.0202.

权重没有变化，却出现了约 2% 的概率比偏移。这是 Spurious Policy Shift（虚假的策略变化），可能影响 clipping 判断和策略梯度。上面的数值只是说明问题的例子，不代表项目测得的典型误差。

真正更新权重后，概率比偏离 1 是正常现象。需要排除的是由不同计算实现引入、与学习无关的额外偏移。

还要区分原始模型概率与经过 temperature、top-p 等处理的采样分布。两端比较的概率定义如果不同，即使底层算子完全一致，也不应期待比率自动等于 1。

2. 同一套公式为什么算不出同一个数

浮点运算通常不满足结合律：

(a+b)+c≠a+(b+c). (a+b)+c\neq a+(b+c). (a+b)+c=a+(b+c).

训练和推理可能使用不同的分块方式、归约顺序、累加精度和舍入时机。BF16、FP16 下，这些差异尤其值得关注。

计算环节 可能产生差异的地方
Attention 对历史 token 的归约、分块和计算路径
RMSNorm hidden dimension 上的平方和与归一化
GEMM 乘加顺序、分块和累加精度
LogSoftmax 词表上的最大值与指数和归约
AllReduce 多 GPU 的通信拓扑与归约顺序

每个算子都可以在数学意义上正确，但最终结果不一定逐位相同。差异经过 Transformer 多层传播后，会体现在 logits 和 logprob 上。

因此，保证单个引擎重复运行得到同样结果，和保证两个不同引擎得到同样结果，是两个不同要求。

3. Numerical Contract：统一的不只是数学公式

RL-Kernel 的思路是为相关算子规定共同的 Numerical Contract（数值执行契约）。

契约不只规定计算什么，还约束：

  • 哪些数据参与计算和归约；
  • 归约与分块的顺序；
  • 中间结果的精度；
  • 舍入和类型转换的位置；
  • 使用的底层数学原语。

训练和推理分别接入符合相同契约的 kernel，才能在指定执行路径上追求严格一致。

提供的材料还区分了两层职责：vime 负责权重版本、token 和训练时间线等系统层对应关系；RL-Kernel 负责数值计算路径。错误的权重同步、过期 KV cache 或输入错位，都不能靠更一致的矩阵乘法修复。

所以，数值一致性应建立在两端确实处理同一份模型状态与输入的基础上。

4. Fused Linear LogP：不保存完整 logits，也能计算目标概率

语言模型通常先通过 LM Head 得到：

Z=HW⊤, Z=HW^\top, Z=HW⊤,

其中 H∈RN×DH\in\mathbb R^{N\times D}H∈RN×D 是隐藏状态，W∈RV×DW\in\mathbb R^{V\times D}W∈RV×D 是词表权重。完整 logits 的大小为 N×VN\times VN×V。

对第 iii 个位置的已采样 token aia_iai​，训练需要的可能只是：

log⁡p(ai)=Zi,ai−log⁡∑j=1Vexp⁡Zi,j. \log p(a_i) =Z_{i,a_i}-\log\sum_{j=1}^{V}\exp Z_{i,j}. logp(ai​)=Zi,ai​​−logj=1∑V​expZi,j​.

常规流程可能先生成完整 logits，再计算 log-softmax 和 gather。词表很大时，中间张量的显存成本十分可观。

Fused Linear LogP 使用分块矩阵乘法和在线 LogSumExp 归约，累计归一化项，同时保留目标 token 的 logit，从而避免在 forward 中物化完整的 N×VN\times VN×V 张量，并支持反向传播。

这里省去的是完整中间矩阵的存储和部分调度开销，不是只计算目标 token、完全跳过其余词表。精确的 softmax 归一化仍依赖其他词表项。

这项优化适合以选定 token logprob 为主要需求的损失。如果还需要完整词表分布、额外的熵或其他统计量，应检查融合路径是否支持对应计算。融合算子也不保证在所有 tensor shape 下都比现有 GEMM 实现快。

5. 一致性实验支持到什么范围

材料记载，v0.1.0 的 Qwen3-8B 测试分别使用：

硬件配置 测试结果
8× NVIDIA H100 200 个训练步骤中，比较的 LogP 逐位差异均为 0
8× AMD MI300X 200 个训练步骤中，比较的 LogP 逐位差异均为 0

严格一致性路径报告的 mismatch_count 和 max_abs_diff 始终为 0，而原生对照路径每步都出现 mismatch。

这支持的是：在这些配置和测量位置上，训练端与推理端的 LogP 可以严格对齐。

它不等于证明 H100 与 MI300X 之间的输出逐位相同，也不等于整个 backward、optimizer state 和长期训练轨迹都完全可复现。两组实验的 batch 配置也不同，不能用来直接比较跨硬件性能。

6. 算子快了多少，训练又快了多少

材料列出一组 Qwen3-30B-A3B、8×H100 的性能实验：

指标 Native vime vime + RL-Kernel
Fused Linear LogP 对应 T3 窗口，Forward + Backward CUDA 时间 33.96ms 18.50ms
完整 RL step 耗时 232.20s 228.40s

算子窗口约加速 1.84 倍，耗时下降约 45.5%，该窗口峰值预留显存降低约 5.6GB。但完整 RL step 只改善约 1.6%。

这并不矛盾。完整训练还包含 rollout、权重同步、通信、调度和其他计算。优化一个占比有限的环节，不能自动获得同等幅度的端到端收益。

因此，使用这些结果时应分别说明：

  • 算子计时还是整步计时；
  • 峰值预留显存还是实际张量占用；
  • 单次计算收益还是完整训练流程收益。

不能把 1.84 倍的算子加速写成 1.84 倍的训练加速，也不能把单窗口节省的显存直接当作整个任务的峰值显存下降。

7. 部署时需要分开检查的三层问题

层次 首先确认什么
模型与输入一致 权重版本、token、位置、mask、缓存和概率定义是否对应
数值执行一致 dtype、归约顺序、并行布局和实际 kernel 路径是否对齐
性能收益成立 显存、算子耗时和完整 RL step 是否分别改善

例如材料提醒，RTX 5090 属于 SM120，而所述 Hopper 专用快路径主要针对 SM90。即使存在 fallback，也需要检查实际 dispatch，不能直接把 H100 的性能数字移植到其他硬件。

这类支持情况会随版本变化。真正复现时，应以所用提交和运行日志确认，分别测量一致性与性能；成功启动不代表进入了预期快路径。

8. 研究价值与局限

RL-Kernel 最有价值的地方，是把 RL 算法中的“相同策略”变成可以在系统层测试的要求。

当概率比出现异常时，原因可能来自真实的策略更新，也可能来自旧策略权重、输入错位或数值计算差异。减少后一类干扰，有助于更清楚地判断算法和训练超参数本身的影响。

但严格 LogP 一致性仍然只是证据链的一部分。要证明它改善最终训练，还需要在相同算法、数据和预算下比较奖励曲线、稳定性与最终能力。不能仅由 mismatch 为 0 推出模型能力必然提高。

现有材料中的严格验证主要围绕特定模型和框架组合。更广泛模型、MoE、并行布局及硬件的覆盖情况，应逐项核对，而不是从一次验证推广到全部配置。

对于后训练系统，这个项目提供的启发是：策略优化所依赖的概率，既是模型的输出，也是执行系统的产物。 算法公式、模型状态和底层计算共同决定了训练是否真的在优化预期的策略。
