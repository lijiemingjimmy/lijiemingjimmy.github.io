Realtime-Bench：想得对，还要来得及做

假设一个 Agent 正在竞价。它看到了当前价格，算出了合理报价，也知道应该点击哪个按钮。问题是，拍卖只剩 5 秒，它却用了 10 秒思考。最后输出的操作即使完全正确，也已经没有执行价值。

Realtime-Bench 研究的就是这类问题：模型在观测时刻想出的动作，到真正执行时是否还有效？ 它用动态网页和游戏，把推理消耗的时间放进任务本身，再用三种时钟区分任务能力、推理长度与实际服务延迟的影响。

论文：Realtime-Bench: Can Frontier Models Solve Real-time Interactive Problems?，Jingyu Tang 等。arXiv:2610.22155，2026 年 10 月 15 日首发，本文核对的是 10 月 22 日更新的 v3。以下沿用附件的解读主线，并补充统计口径与协议边界。

论文元信息｜v3 正文及附录｜项目主页

1. 这个 benchmark 有什么用？

很多交互评测采用这样的循环：给模型一张图，等它想完，执行动作，再给下一张图。环境如果在等待期间冻结，模型就可以无成本地多想一会儿。

真实交互中，车流、库存、截止时间和其他参与者不会一起暂停。长时间思考既可能帮助选对动作，也可能让原来的动作失效。

因此，Realtime-Bench 想区分两种失败：

  • 没想明白。 给足时间，依然理解错任务或选错动作。
  • 想明白得太晚。 能找到合理动作，但行动窗口已经过去。

这一区分有实际用途。前者可能需要更强的理解与规划；后者可能更需要缩短决策、提前执行、改进调度，或者让快速控制模块接管。

例如，同样一个模型在暂停环境时表现好、实际时钟下表现差，继续增加 reasoning effort 未必是有效方向。相反，若取消推理时间成本后仍然失败，就不能只靠更快的 API 解决。

它的核心价值是提供这类诊断对照。一次总成功率能够告诉我们系统是否好用，时钟对照则进一步帮助判断问题出在哪里。

2. “实时能力”被拆成哪三件事？

维度 具体问题 竞价例子
RT-Perceive：时序状态感知 当前状态是什么，观测是否已经过期？ 原来的价格是否仍有效，竞价窗口是否还开着？
RT-Deliberate：自适应推理 还值得花多少时间思考？ 剩 2 秒时是否应该停止继续比较方案？
RT-Act：考虑时机的动作选择 现在行动、等待，还是换一个仍来得及的动作？ 立即提交报价，或判断此刻已经不应出价

三者相互影响。模型可能看见倒计时，却没有因此缩短推理；也可能推理足够快，却反复执行已经失效的旧计划。

这些是论文组织问题和分析失败的维度，不是三套互相独立、各自有严格隔离输入的能力测试。一次失败可能同时涉及状态跟踪、推理时间和动作选择。原文 §3.1

3. 三种 Clock：同样的动作，什么时候生效？

设模型在环境时间 tit_iti​ 收到观测，经过协议规定的延迟 Δti\Delta t_iΔti​ 提交动作：

tiact=ti+Δti. t_i^{\mathrm{act}}=t_i+\Delta t_i. tiact​=ti​+Δti​.

三种协议改变的是这段延迟如何计算。

协议 思考期间环境推进多少 更适合回答什么问题
Wall Clock 按实际推理服务耗时推进 当前模型与服务配置放到动态环境里，实际表现怎样？
Paused Clock 推理本身不消耗环境时间 消除推理延迟后，还有哪些任务做不了？
Token Clock 按生成 token 数映射为环境时间 统一推理长度的时间成本后，能否及时行动？

Wall Clock：把实际等待时间算进去

Δti=Tiinference. \Delta t_i=T_i^{\mathrm{inference}}. Δti​=Tiinference​.

模型请求耗时 8 秒，环境就按这段时间继续演化，随后才执行动作。结果同时反映模型、部署服务、请求处理与通信等因素。

这并不是评测上的缺陷：部署者确实关心端到端等待多久。但若目标是研究模型如何分配推理，服务速度就成了需要控制的变量。

此外，论文的 Wall Clock 也有明确计时范围：GUI 执行延迟不计入环境推进。因此，它是包含实际推理延迟的受控协议，不能理解成操作系统与物理设备全部耗时都按现实原样累计。

Paused Clock：给推理一个理想参照

Δti=0. \Delta t_i=0. Δti​=0.

无论模型想多久，动作都可以在收到观测的那个环境时刻提交。后续环境仍按规则继续推进，等待动作也仍然有任务含义。

这可以观察模型的任务求解能力，但它仍受截图、动作接口和策略错误影响。暂停推理也不意味着整个 episode 永远冻结。

将它视为理想化参照比较准确；不能预先认定它对每个模型、每次随机运行都是严格的分数上界。

Token Clock：用推理长度计算代理时间

设 fff 为每仿真秒的观测帧数，BBB 为一个观测间隔对应的 token 数，nin_ini​ 为本次计费的生成 token 数：

κ=Bf,Δti=niκ=niBf. \kappa=Bf, \qquad \Delta t_i=\frac{n_i}{\kappa}=\frac{n_i}{Bf}. κ=Bf,Δti​=κni​​=Bfni​​.

主实验设置 f=1f=1f=1 FPS、B=64B=64B=64，即每 64 个计费 token 对应 1 秒仿真时间。一个 200-token 响应产生：

Δt=20064=3.125 s. \Delta t=\frac{200}{64}=3.125\ \mathrm{s}. Δt=64200​=3.125 s.

在还剩 5 秒的竞价窗口里，它可能来得及；在需要更早转向的贪吃蛇里，就可能已经错过时机。同样长度的回答是否有用，取决于任务的机会窗口。原文 §3.2、Figure 4

4. Token Clock 标准化了什么，又留下什么差异？

它固定了“一个计费 token 对应多少仿真时间”。相同 token 数不会因为某家 API 更快而获得更早的动作时间，这让推理长度的代价更容易比较。

但 token 数不是统一的计算量。不同 tokenizer、内部推理实现、并行计算方式和 usage 上报口径，都可能影响比较。相同长度的文字，也未必对应相同 token 数。

原文附录按完整响应的 API usage 计入 reasoning 与输出 token。这里需要理解的是总的计费生成量，实际实现应避免把已经包含 reasoning 的总量再重复相加。可见回答简短，不一定意味着内部推理开销很小。原文附录 A.2

另一个重要区别是：Token Clock 不要求真实服务器恰好以 64 token/s 生成。它可以等模型完成，再按 token 数决定动作在仿真中何时生效。这个实验模拟了生成长度造成的时间成本，不直接等同于真实并发推理系统。

因此，两种指标各有用途：Wall Clock 适合看当前端到端服务表现，Token Clock 适合控制部分服务速度差异。两者一起看，信息比任意一个单独排名更完整。

5. 任务和 Agent 接口是什么样？

完整任务集包含 50 个任务：30 个 Web、20 个 Game。网页覆盖竞价、预约、订单和限时交易等情境；游戏包含移动障碍、短暂转向窗口和倒计时决策。

官方公开框架开放其中 20 个任务（12 Web、8 Game），另外 30 个用于私有评测。用公开部分跑出的成绩，应明确标为公开子集结果，不直接与完整 50 任务成绩混用。官方提交说明

这些环境的关键性质是：即使模型不行动，状态也会随时间变化。成功同时取决于动作内容与提交时刻。

观测使用 1 FPS 的截图，最长边缩放至 768 像素，同时提供只读的 Set-of-Marks（SoM）信息，说明当前可交互元素、语义与支持的动作。输出是 click、type、key、drag、wait 等 GUI 操作。

SoM 的目的，是减少界面定位对实验的干扰。它也改变了能力边界：这不是纯靠原始像素自行发现所有交互元素的评测，模型获得了额外的界面语义辅助。

历史上下文采用分块截断，尽量保留不变的前缀，减少频繁修改历史造成的重复 prefill。这是影响实际延迟的 harness 设计，但是否复用到缓存，还取决于具体服务支持。原文 §4–5、附录 A

1 FPS 不等于模型每秒一定能做一次决策

1 FPS 规定的是观测调度间隔。如果一次推理跨过多个间隔，中间帧会跳过，下一轮获得的是当时最新的调度帧。模型不会在当前这次推理中自动读到每一帧。

反过来，即使推理很快完成，也不会额外获得一张不在既定时间网格上的观测。观测频率、决策完成速度和环境内部动画更新速度，是三个不同概念。

6. Pass³ 和 Pass@3 到底怎么读？

每个任务做三次独立尝试。记任务 jjj 在第 rrr 次运行是否成功为 yjr∈{0,1}y_{jr}\in\{0,1\}yjr​∈{0,1}，共有 NNN 个任务。

三次运行的平均成功率为：

Pass1=Pass@1=13N∑j=1N∑r=13yjr. \mathrm{Pass}^{1}=\mathrm{Pass}@1 =\frac{1}{3N}\sum_{j=1}^{N}\sum_{r=1}^{3}y_{jr}. Pass1=Pass@1=3N1​j=1∑N​r=1∑3​yjr​.

三次全部成功的任务比例为：

Pass3=1N∑j=1N∏r=13yjr. \mathrm{Pass}^{3} =\frac{1}{N}\sum_{j=1}^{N}\prod_{r=1}^{3}y_{jr}. Pass3=N1​j=1∑N​r=1∏3​yjr​.

至少一次成功的任务比例为：

Pass@3=1N∑j=1N[1−∏r=13(1−yjr)]. \mathrm{Pass}@3 =\frac{1}{N}\sum_{j=1}^{N} \left[1-\prod_{r=1}^{3}(1-y_{jr})\right]. Pass@3=N1​j=1∑N​[1−r=1∏3​(1−yjr​)].

一个任务结果为“成功、失败、成功”，它对平均成功率贡献 2/32/32/3，对 Pass³ 贡献 0，对 Pass@3 贡献 1。

所以，Pass³ 不能用总体平均成功率的三次方替代。任务难度不同，重复运行的结果也有具体分布；这几项指标是在回答不同问题。

44%、42.67% 和 36% 并不冲突

论文 v3 附录中，GPT-6 Astra（high）三次运行成功率分别为 42%、42%、44%。因此：

统计口径 数值 含义
最好一次运行 44% 某次运行在 50 个任务上成功 22 个
三次平均 Pass¹ / Pass@1 42.67% 三次运行平均表现
Pass³ 36% 18 个任务三次全部成功

开头常见的“最佳成功率 44%”说的是最好一轮，不是三次平均值。Pass³ 对重复稳定性更严格，但只有三次试验也无法据此认证长期可靠性。原文附录 B.1，Tables 2–4

7. 实验的核心发现：时间改变了推理的收益

三种时钟下，表现差异很大

下面列出 Figure 5 中高 reasoning effort 的四个模型，数值为该图的任务成功率：

模型 Wall Clock Paused Clock Token Clock
GPT-5.6 Sol 8% 58% 36%
Claude Opus 5 14% 70% 30%
Gemini 3.8 Flash 24% 70% 34%
Kimi-K3 6% 80% 36%

这组数是跨时钟实验的口径，不能将它的 Wall 列写成附录三次运行平均值。GPT-6 Astra 没有进入这组六模型的跨时钟对照，也就不能从这里推断它的 Paused 或 Token 成绩。原文 Figure 5、§6.1–6.2

Kimi-K3 的 80% 与 6% 说明，给足无成本的推理时间，与要求及时行动，是非常不同的条件。Token Clock 中仍有明显下降，则表明服务速度并不能解释全部差异：推理长度本身也会消耗行动机会。

但这些差距不是严格可加的因果分解。不同协议会改变后续观测、动作和轨迹，不能简单拿两个分数相减，就宣布精确测出了某个模块的贡献。

提高 reasoning effort，收益可能反转

Claude Opus 5 在 Paused Clock 下由 low 的 62% 提高到 high 的 70%；在 Token Clock 下，却由 44% 降到 30%。

这说明额外推理在没有时间惩罚时有帮助，加入时间成本后却可能得不偿失。同时，Kimi-K3 在 Token Clock 下由 24% 提高到 36%，所以结论也不能写成“实时任务一律应该减少思考”。

真正需要适应的是当前任务的时间余量，以及多想一会儿能带来多少决策收益。原文 §6.2

响应很快，也不能替代正确判断

附件引用 Jev 1.13 的平均延迟 0.469 秒、Pass³ 为 8%，说明低延迟系统也可能表现有限。但原文另有一个重要条件：Jev 只评测 Web 任务，并使用结构化文字观测。 因此，这组分数不适合直接和覆盖完整任务集的视觉模型作公平的能力排名。

更可靠的判断方式，是在相同任务、相同信息输入和相同计时规则下，同时检查延迟与成功率。原文附录 A.4、B.1

8. 失败分析：迟到、没更新状态、选错时机

论文中的一个五子棋案例很直观：只剩 10 秒行动窗口，模型生成 1,845 个 token。在默认 Token Clock 下：

Δt=1845/64≈28.83 s. \Delta t=1845/64\approx28.83\ \mathrm{s}. Δt=1845/64≈28.83 s.

即使最后选到好落点，也已经超时。这主要反映没有按紧迫程度分配推理。

另一类案例是：新画面已经要求转向，模型却继续沿旧方向移动；还有一类是在应该立刻行动时继续等待。这些错误说明，实时性不仅是压缩输出长度，还包括更新内部状态和判断何时需要动作。

值得注意的是，论文对状态跟踪和行动必要性的分析使用了 Paused-High 条件。暂停的是每次推理期间的时间成本，动作之间环境仍会变化。这有助于观察模型是否连已经收到的新状态都没有正确利用，而不是将所有错误归咎于推理时环境跑得太快。原文 §6.3、附录 C

失败标签是根据轨迹与视频进行的定性归因。它能提供调试线索，但不能像干预实验那样证明某个内部机制就是唯一原因。例如“依赖旧文本过多”是解释假设，仍需要专门实验验证。

9. 为什么它还不能完整评估 Full-Duplex Agent？

这里有两个容易混在一起的问题：

  1. 环境是否在模型思考期间继续变化？
  2. 模型是否能在同一次思考期间接收新信息，并取消或修改旧动作？

Realtime-Bench 的主协议明确覆盖第一项。第二项则需要额外的并发、抢占和动作更新机制。

主评测中，一次生成跨过的中间观测可以被跳过，模型完成后再接收最新调度帧。这与“推理中不断注入新观测、立即撤回旧计划”有实质区别。

可以用一个例子区分：Agent 开始规划拿杯子，思考到一半时杯子被人拿走。顺序式协议可能先提交旧动作，再到下一轮发现变化；可抢占系统则可能在动作下发前就撤销它。两者都可能运行在动态环境里，却不具备同样的交互能力。

因此，环境不暂停是评估实时性的一个重要条件，尚不足以单独验证全双工能力。还应测试新信息何时进入模型、旧动作何时可以撤销、底层执行是否继续，以及多个过程怎样协调。

当前官方框架另外提供 streaming 交互模式，将帧推送到 live session，但文档要求单独报告，不进入 turn-based 排行榜。当前接口通过 rtbench run --ak interaction_mode=streaming 选择模式；附件中的“streaming-run”应理解为流式运行方式，不宜当成当前 CLI 子命令。官方 Streaming runs 文档

论文版本与当前框架要分开记录

还有一处复现时值得注意的文档差异：论文 v3 写明 GUI 执行延迟不推进环境时间；当前仓库 main 的 Clock 表则将 observation、network、inference 和 action latency 都列入 Wall Clock。这是两份文档之间的差异，本次未通过源码执行确认其历史实现变化。

因此，复现时应固定代码 commit，并核查实际计时路径。本文对论文成绩的解释仍以 v3 协议为准，当前框架说明另列。当前时钟文档

10. 如果迁移到机器人，应该补哪些测量？

以下是基于论文提出的研究设计建议，不属于作者已经完成的机器人实验。

机器人里，动作有效性不仅受到推理耗时影响，还受到感知传输、指令排队、控制器接收和执行器响应影响。应为关键事件保留时间戳，而不是只记录 API 请求用时。

一个有用的定义是动作信息年龄：

ActionAgei=tieffective−tiobservation. \mathrm{ActionAge}_i =t_i^{\mathrm{effective}}-t_i^{\mathrm{observation}}. ActionAgei​=tieffective​−tiobservation​.

其中 tieffectivet_i^{\mathrm{effective}}tieffective​ 要明确规定，例如控制器接受该指令的时刻，而不是事后任意选择的动作完成时刻。对于多帧输入，还需说明使用哪一帧作为参考。

指标 帮助回答什么问题
任务成功率与重复成功率 任务是否完成，重复执行是否稳定？
Action Age 动作依赖的信息已经多旧？
Deadline miss rate 有多少次必要决策错过时间窗口？
Interruption latency 新事件发生后，旧动作多久被取消或替换？
延迟的中位数与高分位数 偶发长等待是否拖垮系统？
底层控制连续性 高层推理时，机器人是否继续维持稳定控制？

还需要区分三个时间尺度：高层 Agent 决定任务与技能，中层策略生成动作段，底层控制器维持快速反馈。一个高层调用耗时几秒，是否有害，取决于这期间谁在控制，以及任务是否允许等待。

例如，慢速整理桌面与防止杯子滑落具有完全不同的响应要求。不能把论文的 1 FPS 观测和 64 token/s 时间映射直接当成机器人操作的通用设置。

同步与异步系统怎样公平比较？

可以固定任务、初始条件、信息输入和总资源预算，比较顺序决策与并发控制。除了成功率，还要记录各模块的推理次数、计算用量和实际时间。

异步系统若同时运行两个模型，性能提升可能来自架构，也可能来自更多计算资源。固定 token 数仍不能完全固定计算量，因此应把资源口径与端到端延迟一并公开。

对失败也要区分：是高层迟迟不给新目标、底层没有恢复能力，还是取消命令没有及时生效？这比统一记为“模型反应慢”更有助于改进系统。

11. 和相近工作、前面的 QCP 放在一起看

Real-Time Reasoning Gym / AgileThinker

Real-Time Reasoning Agents in Evolving Environments 已研究动态环境中的推理时间成本，并提出同时进行快速反应和较慢规划的 AgileThinker。因此，不宜把 token 时间代理或快慢推理分工作为 Realtime-Bench 首次提出的思想。

Realtime-Bench 更值得借鉴的是统一的三时钟对照，以及将这一问题落到多模态网页与游戏交互的评测设计。

名字相近的另一套 RealtimeBench

The World Won't Wait: Evaluating and Teaching Agents Under a Live Clock 是另一篇论文，包含六类游戏的 180 个任务，并提出 TORSI：慢速 teacher 在执行间隙离线分析和改进指导，快速 student 在实时阶段独立行动。

它将更多计算放在实时执行之外。这与让两个模块在执行期间并行工作的方案不同，也不是本文 50 任务 Realtime-Bench 的组成部分。引用时应保留完整标题和论文编号，避免名称混淆。

QCP：控制执行速度，与控制推理延迟不是一回事

前面的 QCP 笔记 讨论的是成功执行的速度、平滑性与稳定性怎样作为策略条件；Realtime-Bench 讨论的是模型做出决策前的等待怎样改变任务结果。

一个策略动作很快，但开始行动之前等待很久，仍可能错过机会。反过来，Agent 很快给出指令，但底层运动慢，也可能来不及完成任务。

如果研究机器人端到端实时能力，两种时间都需要计入。进一步的组合方向是：高层根据剩余时间调整推理与技能选择，底层根据质量条件调整执行方式，再用闭环反馈判断是否仍然来得及。

12. Discussion：把“何时行动”纳入能力定义

可以用一个概念性目标表达这篇工作的启发：

max⁡n,a  E[R(st+Δt(n),a)∣ht]. \max_{n,a}\; \mathbb E\left[R\bigl(s_{t+\Delta t(n)},a\bigr)\mid h_t\right]. n,amax​E[R(st+Δt(n)​,a)∣ht​].

这是本文的理解示意，不是论文提出的新训练算法。模型既要选择动作 aaa，也要决定为这个动作投入多少推理 nnn。更多推理可能改善判断，却同时让执行发生在更晚的状态。

Realtime-Bench 把这件事变成了可做对照的实验。它没有直接解决自适应推理、连续感知或动作抢占，但提供了一个清楚的检查方式：同一系统在取消时间成本、引入统一代理时间和计入实际延迟时，分别会发生什么。

对 Robot-Use Agent，最有价值的下一步是把这个检查方式延伸到真实执行链路：当高层还在思考，底层在做什么；当新信息使旧计划失效，系统多久能改；当动作终于生效，它是否仍在解决当前问题。
