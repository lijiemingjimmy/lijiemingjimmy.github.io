Retargeting Through Reasoning：让 Agent 在仿真里改出能用的人形机器人动作

人类示范给出“要让物体发生什么变化”，Agent 通过写代码、运行仿真、检查失败，寻找机器人做得到的交互方式。

原文：Retargeting Through Reasoning for Humanoid–Object Interaction（CMU、FieldAI、Caltech，2026 年 11 月 6 日项目博客）。

附件称它为 HuMoTAR，官方页面的 BibTeX key 也包含 humotar，正文这里使用正式标题。下文的公式用于解释机制，不冒充作者公布的精确实现。

1. 搬椅子时，到底应该模仿什么？

人用一只手提起椅背，走几步，再把椅子放下。让 G1 复现这段示范，有两件不同的事：身体姿态接近人，以及确实把椅子搬到指定地方。

这两件事可能冲突。人的手能扣住椅背，机器人的手未必可以；人的身高、手臂长度、抓握能力，也与 G1 不同。关节轨迹看起来很像，实际执行却可能根本没抓住椅子。

这篇工作的选择是：优先保留物体交互的结果，允许机器人改变抓法、姿态和控制方式。 人单手提，机器人可以双手托；人直接抬，机器人可以先调整站姿和接触位置。

可以用两个概念性目标理解这个变化：

身体运动相似：min⁡QDbody(Q,H) \text{身体运动相似：}\quad \min_Q D_{\mathrm{body}}(Q,H) 身体运动相似：Qmin​Dbody​(Q,H)
物体交互相似：min⁡PDobject(O(Sim⁡(P)),O∗). \text{物体交互相似：}\quad \min_P D_{\mathrm{object}}\bigl(O(\operatorname{Sim}(P)),O^*\bigr). 物体交互相似：Pmin​Dobject​(O(Sim(P)),O∗).

其中，HHH 是人类动作，QQQ 是机器人运动，PPP 是可执行程序，O∗O^*O∗ 是参考物体轨迹。第二个目标允许改变程序，只要仿真中产生了合适的物体运动。

这里的“语义”有很具体的落点：椅子被抬起、运输、放下，而非只把终点位置对上。物体轨迹可以记录过程，但完整任务是否成立还可能涉及接触、稳定性、释放等条件。

已有重定向方法也会考虑接触和物体关系。这项工作值得关注的新增部分，是让 Coding Agent 在仿真反馈下反复修改运动和控制代码，扩大可以搜索的执行方案范围。

2. 整个系统怎么工作？

主实验提供的输入相当充分：SMPL 人体动作、HOI-Retarget 生成的初始运动学参考、任务场景，以及按机器人尺度调整过的目标物体轨迹。

人类示范 + 初始参考 + 场景 + 目标物体轨迹
                         ↓
               Agent 编写 Python 程序
                         ↓
         全身参考运动、手部运动、控制修改
                         ↓
          SONIC + Dex3 控制 → MuJoCo 执行
                         ↓
      执行图像、物体轨迹误差、接触测量
                         ↓
              Agent 检查失败并修改程序

项目使用 GPT-6 Astra 在 Codex 环境中完成程序生成和迭代。SONIC 提供全身控制能力；Agent 可以补充或替换其关节角输出。Dex3 手部采用阻抗控制，MuJoCo 负责模拟实际接触和物体运动。方法说明

例如，第一次运行时手没碰到衣架，反馈会促使 Agent 检查手部局部图像、调整抓取位置；下一次衣架被抬起来，但转弯时滑落，就需要检查手部姿态、身体运动和接触保持。这个例子解释的是迭代思路，具体修改仍取决于每次仿真证据。

优化对象是程序及其产生的运动与控制。 当前实验没有为每个任务重新训练一个神经策略，也没有进行任务特定的 RL 微调。

两种闭环要分开

开发阶段的闭环是：

Pk+1=Agent⁡(Pk,Feedback⁡(Sim⁡(Pk))). P_{k+1}=\operatorname{Agent}\bigl(P_k,\operatorname{Feedback}(\operatorname{Sim}(P_k))\bigr). Pk+1​=Agent(Pk​,Feedback(Sim(Pk​))).

Agent 看完一次执行，再改代码、重跑。它可以花几十分钟乃至两个小时改善一个任务。

执行阶段的闭环则是控制器根据当前状态持续调整动作。SONIC 等底层控制可以包含状态反馈，但这不能直接说明高层 Agent 已经能在陌生场景里实时应对意外。两层闭环解决的时间尺度和问题不同。

3. 结果说明了什么？

实验平台是 MuJoCo 中的 G1 + Dex3，任务来自 HUMOTO 和 OMOMO，各 20 个。传统对照是作者适配到这一平台的 HOI-Retarget + SPIDER；迭代方案每任务分配两小时预算。

方法 HUMOTO OMOMO 总成功率
HOI-Retarget + SPIDER 25%，5/20 10%，2/20 17.5%，7/40
Astra 单次生成 5%，1/20 0%，0/20 2.5%，1/40
Astra 仿真迭代 80%，16/20 70%，14/20 75%，30/40

这里最值得注意的是单次生成只有 2.5%。能写出控制程序，只是起点。物理执行是否成立，需要经过验证；这套系统的主要收益出现在反复运行、检查和修正之后。

成功率采用 Semantic Success：GPT-6 Astra 比较人类与机器人执行视频，判断交互是否完成，输出 PASS/FAIL。它不是一个单纯按位置误差阈值算出的成功率。生成方案与评判方案使用同一模型家族，因此独立物理判据和人工一致性检查会让结果更有说服力。

物体跟踪另用 Mean ADD 衡量，越低越好：

Astra 单次生成 56.09 cm 69.87 cm 62.98 cm

4. ADD 到底在测什么？为什么不能只看物体中心？

这一节展开附件最后提出的问题。

假设参考物体位姿为 (R∗,t∗)(R^*,t^*)(R∗,t∗)，执行位姿为 (R,t)(R,t)(R,t)，在物体自身坐标系采样一组点 V={v1,…,vM}V=\{v_1,\ldots,v_M\}V={v1​,…,vM​}。同一个物体点在两个位姿下的世界坐标分别是：

xi=Rvi+t,xi∗=R∗vi+t∗. x_i=Rv_i+t,\qquad x_i^*=R^*v_i+t^*. xi​=Rvi​+t,xi∗​=R∗vi​+t∗.

标准 ADD 的概念是：

ADD⁡=1M∑i=1M∥(Rvi+t)−(R∗vi+t∗)∥2. \operatorname{ADD} =\frac{1}{M}\sum_{i=1}^{M} \left\|(Rv_i+t)-(R^*v_i+t^*)\right\|_2. ADD=M1​i=1∑M​∥(Rvi​+t)−(R∗vi​+t∗)∥2​.

也就是把两种位姿下的物体叠在一起，测量对应点平均错开了多远。它同时受到平移、旋转和物体几何形状影响。

情况一：方向正确，只平移错了 10 cm

如果 R=R∗R=R^*R=R∗，则每个点的偏差都是 t−t∗t-t^*t−t∗：

ADD⁡=∥t−t∗∥2=10 cm. \operatorname{ADD}=\|t-t^*\|_2=10\text{ cm}. ADD=∥t−t∗∥2​=10 cm.

此时 ADD 就是平移误差。

情况二：中心正确，但物体转歪了

中心相同并不意味着任务正确。桌子可能倾斜，椅子可能倒置，衣架可能横过来。

对距离旋转轴 rrr 的一个点，旋转偏差 θ\thetaθ 导致的位移为弦长：

d=2r∣sin⁡θ2∣. d=2r\left|\sin\frac{\theta}{2}\right|. d=2r​sin2θ​​.

当 r=0.5r=0.5r=0.5 m、θ=10∘\theta=10^\circθ=10∘ 时，这个点偏移约 8.72 cm。它只是单点的例子，整个物体的 ADD 需要对所有采样点平均。

这也解释了一个评测细节：相同的角度误差，在大物体上可能产生更大的厘米误差。跨物体比较时，最好同时报告位置误差、角度误差；若使用按物体尺寸归一化的 ADD，也应另列指标，保留原始单位。

此外，上式比较的是同一个点，不是每个点都寻找最近邻。对有旋转对称性的物体，有些姿态差异在语义上可能等价，因此 ADD 与任务是否成功仍需要分别判断。

时间对齐为什么重要？

人类两秒完成抬起，机器人四秒完成。如果强行比较相同时间戳，人已经举起椅子而机器人还在起步，误差会很大；但它们可能完成了同一交互，只是速度不同。

项目因此比较对应的运动阶段。可以用一个概念性的阶段映射 ϕ(k)\phi(k)ϕ(k) 表示：

ADD⁡‾=1K∑k=1KADD⁡(Tϕ(k)robot,Tkref). \overline{\operatorname{ADD}} =\frac{1}{K}\sum_{k=1}^{K} \operatorname{ADD}\bigl(T^{\mathrm{robot}}_{\phi(k)},T^{\mathrm{ref}}_k\bigr). ADD=K1​k=1∑K​ADD(Tϕ(k)robot​,Tkref​).

公开文字没有给出完整的对齐算法，因此不能直接断言它使用了 DTW。

阶段对齐让“动作比较慢但做对了”得到更合理的评价，但也改变了指标回答的问题：它更强调交互路径，弱化了执行速度。评测实时能力时，还需要单独记录耗时、停顿、反馈延迟。

一个好的对齐方式还应保留事件顺序。若允许任意找最接近的时刻，机器人先放下再抬起，也可能被错误地匹配成先抬起再放下。这里是指标设计上的提醒，不能据此认定作者的实现存在这个问题。

5. 多给时间、多开 Agent、给经验，分别有多少用？

延长单 Agent 搜索

30 分钟预算的最终成功率为 47.5%，120 分钟为 75%。这两项来自独立预算运行，不应直接当作同一次运行在两个时刻的成功率。

博客还画了 best-so-far ADD：30 分钟 29.59 cm，120 分钟 10.21 cm。它记录截至当前找到的最好方案，与主结果中的整体 ADD 12.63 cm 是不同口径，覆盖任务数也有差别，不能混写。

更长时间可以带来更多有效尝试。不过，当前证据展示的是这两个预算下的改善，还不足以拟合一个普遍的 scaling law，更不能保证继续延长时间一定有效。

四 Agent 的优势主要体现在哪里？

配置 墙钟时间 分配的 Agent-hours 成功率
单 Agent 30 分钟 0.5 47.5%
四 Agent 独立搜索 30 分钟 2 52.5%

同样等待半小时，协作方案表现最好；同样分配两 Agent-hours，单 Agent 连续搜索表现更好。前一个比较回答“多久拿到方案”，后一个回答“如何分配总搜索资源”。

这里的 Agent-hours 是分配预算，不能直接等同于实测 FLOPs、token 用量或 API 费用。协作通信、仿真次数与推理长度都可能不同。

协作也有比简单重复采样更具体的作用：交换失败经验、减少重复试错，以及互相检查遗漏的失败。它是否始终划算，仍需要在更多任务和预算点上测量。预算实验与协作附录

经验能不能迁移？

架子扶正实验从同一个已优化 15 分钟的初始方案出发，再各运行 15 分钟。一组额外获得其他四个家具交互任务的经验摘要，一组没有。

最终物体跟踪误差为：无经验 23.35 cm，有经验 7.77 cm。

经验的载体是策略及成败摘要，可以理解为把过去试验的结果写进上下文。这为可复用技能经验提供了一个具体案例，但目前只是一个目标任务的对照。要证明稳定迁移，还应考察多个新任务、不同摘要来源，以及不相关经验会不会误导搜索。

7. 对 Robot Agent 和技能库研究有什么启发？

我更愿意把它理解为一个利用仿真反馈合成动作程序的系统。它把基础控制器、代码生成和物理验证连接起来，让机器人技能的开发过程可以由 Agent 参与。

对 RUA / Dex-RUA，值得借鉴的是把评测权限和成本写清楚：

需要明确的条件 它会影响什么
是否提供目标物体轨迹 Agent 是否已拿到详细的过程目标
是否能读取精确物体位姿与接触 感知难度与反馈精度
是否可以重置、重复执行 能否依靠离线试错搜索
是否能改底层控制器 可搜索方案的范围
最终程序是否冻结后再测 测到的是现场调参还是可复用技能
是否测试新初始状态、物体与扰动 能否判断执行方案的泛化能力

这些权限对离线技能开发完全有价值。关键是按实际设定解释结果，并把开发预算与最终执行成本分别记录。

一个自然的后续实验是：先在一组任务中搜索程序，把接触策略、控制参数、失败条件和修复方法存成技能库；再固定经验库，在未见任务上测量成功率、所需仿真次数和总成本。这样才能判断经验究竟减少了多少重新试错。

与本地的 Metatron 笔记 可以对照阅读：共同关心的是高层程序与低层运动能力之间的接口。这篇工作的鲜明之处，是把物体交互误差作为迭代证据，并允许修改接触与控制方案。本文不据此做两个系统的性能比较。

8. 我最在意的边界

物理可行性依赖机器人本身。 项目展示的盘子旋转失败中，反复修改手指位置、尝试双手支撑，仍无法稳定完成动作。搜索可以找更好的策略，但硬件形态、可施加的力和接触条件会限制解的存在。

仿真成功还需要经过扰动与真机检验。 当前没有任务特定策略训练或硬件部署；用优化后的参考训练更稳健的策略，是作者列出的未来方向。固定初始状态下找到一个好方案，也不代表它能应对摩擦变化和外部碰撞。

75% 需要连同任务集、预算与评判方式一起读。 它说明这套迭代系统在所选仿真任务中很有效，但单次生成、传统优化、迭代 Agent 之间同时存在工具使用、搜索预算和表达能力的差异。进一步拆分这些因素，才能知道提升分别来自哪里。

对我来说，这篇工作的价值在于展示了一条可操作的技能开发路径：先明确物体应该发生什么变化，再让 Agent 用实际执行证据修改程序。下一步最有价值的验证，是把搜索出的程序冻结下来，看它在新条件下是否仍然可靠，以及过去的经验能否持续降低新任务的开发成本。
