RoboSkills：给 Coding Agent 一套机器人工具，再让它写出可执行的技能

让机器人把红色积木叠到蓝色积木上，至少要做几件事：找到两个物体，估计位置，选择抓取姿态，规划运动，放下之后检查有没有叠稳。RoboSkills 把这些环节组织成 Coding Agent 可以调用的工具和流程，让 Agent 用代码完成任务，也可以反复实验，写出以后能够独立运行的机器人程序。

它最值得关注的地方，是把“在线操作机器人”和“开发机器人技能”放进了同一套工具体系，同时保留两种不同的评测方式。 前者每轮都可以问 LLM 下一步怎么办；后者在开发阶段用 LLM 调试，测试阶段运行冻结的程序。

项目由 OpenRoboKit 开源，仓库采用 MIT License。本文基于提供的解读整理，并核对官方仓库与工作流文档；核对日期为 2026 年 11 月 1 日。它目前适合按一个工程框架来理解，讨论重点是接口、执行机制与评测口径。

1. Tools、Skills、Workflows 分别解决什么？

这三个词容易混在一起，但区分之后，整个项目就清楚了。

层次 提供什么 可以怎么理解
Tools 分割、三维重建、运动规划、仿真、渲染等可调用能力 能实际干活的工具
Skills API 用法、坐标约定、操作步骤、检查方法 怎样把工具用对的说明
Workflows Agent 的运行方式、反馈、实验预算、提交与评测流程 一次任务怎样从开始走到结束

例如，分割工具能根据文字找物体，但它不会自动决定“先抓哪个”。运动规划器能寻找可达路径，但它需要一个合适的目标姿态。Skill 会告诉 Agent 如何组织观察、抓取、检查和重试；Workflow 再决定它能否重置环境、是否能看到成绩，以及最终交付在线执行结果还是一份程序。

因此，一个系统表现好，可能同时受益于模型、工具和说明文档。评价时需要把这些贡献拆开。RoboSkills 所说的 minimal，强调各工作流的实现规模控制在千行以内；完整系统还依赖感知模型、规划器、模拟器等，不能把这个数字理解成全部机器人能力只需要千行代码。仓库介绍

2. 五条工作流，分别在测什么？

工作流 Agent 主要做什么 最终产物或结果 理解时抓住什么
Agent as Policy 边观察边写代码调用机器人 当前回合的执行结果 LLM 持续参与高层决策
Auto Research 在开发环境中尝试、调试、提交程序 冻结的 solve(bot) 测试时不再用 LLM 修改决策逻辑
Agentic Simulation 构建仿真任务，再求解任务 任务与解法 允许使用仿真特权信息，任务生成与求解分开
Real2Sim 组织视频重建、重定向和物理重放 仿真场景与轨迹 视觉重建后还要处理接触和动力学
Motion Generation 生成或迁移动作，检查渲染 角色或机器人动画 主要是运动学流程，不保证物理可执行

这五条流程共享一些工具，但信息条件和输出目标不同。把它们全称为“机器人自主学习”会掩盖差别。特别是 Agentic Simulation 允许特权信息，不能直接与只通过公开机器人接口操作的流程合并比较。五条流程总览

另外，Real2Sim 与 Motion Generation 都提供能够脱离 Agent 运行的固定流水线。Agent 的价值在于选择、连接和修改步骤，处理标准流程之外的需求；流水线能够执行多少工作，也应该计入系统已有能力。

3. Agent as Policy：让 LLM 在观察与动作之间写代码

可以用下面这个简化表达理解它：

ct=LLM⁡(ht,T),(st+1,yt)=Execute⁡(ct,st). c_t=\operatorname{LLM}(h_t,\mathcal T), \qquad (s_{t+1},y_t)=\operatorname{Execute}(c_t,s_t). ct​=LLM(ht​,T),(st+1​,yt​)=Execute(ct​,st​).

hth_tht​ 是历史观测与反馈，T\mathcal TT 是工具及说明，ctc_tct​ 是本轮生成的代码，yty_tyt​ 是执行后的图像、文字或错误反馈。这是对工作流的概括，不是项目新增的学习目标。

拿叠积木来说，一次比较完整的操作可以分成：

  1. 读取 RGB-D、相机参数和点云，找到红色与蓝色积木。
  2. 分割并融合观测，估计物体尺寸、位置和朝向。
  3. 选择抓取姿态，规划接近、闭合夹爪和抬升动作。
  4. 执行后检查物体是否跟着手移动。
  5. 根据蓝色积木的位置生成放置目标，再规划、执行和检查。

LLM 主要决定对象、目标、顺序和失败后的调整；几何计算、逆运动学与轨迹执行由工具承担。运行时保留 Python 变量，所以 Agent 可以维护已经识别的对象、哪只手持有什么、任务进行到哪一步。Agent as Policy 文档

这里的 Stateless 需要按范围理解：工具不会替 Agent 持续管理全部对象和持物关系，并不意味着模拟器没有状态，也不意味着 Agent 每次推理都从零开始。

抓取接口也不是一句“抓住它”就解决所有问题。官方操作说明中的启发式抓取路径仍要求调用者选择抓取位姿；规划成功只说明找到满足相应规划条件的运动，物体是否真正被抓起，还要执行后检查。

4. 成功操作背后，Skill 已经提供了多少知识？

官方 Skill 包含相当具体的操作经验：接近物体、抬升验证、根据实际持物关系更新状态、动作后重新规划，以及失败后改变抓取方向或目标。它还说明坐标和单位，避免 Agent 把数值含义弄错。操作说明原文

这些说明有实际价值。比如夹爪闭合了，可能是抓住物体，也可能只是夹空；“执行抬升，再看物体是否一起移动”就把一个模糊判断变成了可观察的检查。又比如运动规划依赖起始状态，机器人移动后继续复用旧计划，可能造成状态不一致，因此需要重新规划。

但评测时也要问：Agent 自己发现了多少策略，Skill 已经告诉它多少？一个合适的实验设计是固定工具，分别提供 API 说明、加入操作流程、再加入失败恢复规则，观察成功率和调用成本怎样变化。这样才能看出收益来自哪里。

另一个细节是反馈权限。该流程隐藏原生评分，但仍会返回运动状态、误差、图像和回合结束等信息。隐藏分数不等于没有反馈；回合结束也不能直接当成成功标签。 是否完成任务，需要结合具体反馈含义判断。

它也不天然等于实时控制测试。公开说明中，机器人运动通过 execute 推进；LLM 思考期间环境是否继续变化，还要看适配器和时钟协议。因此，这里的闭环交互能力，与 Realtime-Bench 所讨论的墙钟延迟压力应分别评测。

5. Auto Research：先用 LLM 做实验，再留下一个程序

Auto Research 把交付对象从“一次成功操作”变成“一个能重复运行的解法”。

开发场景中观察和尝试
        ↓
分析执行反馈，修改策略代码
        ↓
submit：在开发案例上评测 solve(bot)
        ↓
继续修改，或结束研究
        ↓
选择开发集表现最好的提交，冻结为 solution.py
        ↓
在验证／测试案例中运行固定程序

几个入口的含义很关键：

入口 作用
reset(case=None) 开启新的开发回合，返回上一回合结果与剩余预算
submit(source) 提交定义 solve(bot) 的源码，在开发案例中运行
finish 结束研究，选出程序，再进入后续评测

公开文档规定，最终按开发集成功次数选择提交，平分时选择较新的提交。提交程序必须能在新的执行上下文中运行，不能依赖研究阶段交互窗口里临时保存的变量。文档给出的 RoboDojo 示例使用 Layout 10、11 开发，Layout 0–4 测试；划分由配置指定，不能当成整个项目唯一固定的协议。Auto Research 文档

默认预算是 5 次重置、3 次提交，源码实际限制超额调用，不合法的程序提交不扣次数。这不等于整个研究只运行 5 个回合，因为每次提交还会在开发案例上另行评测。开发反馈包含 success/score/reason/steps，验证和测试结果不回传给研究 Agent。因此，“不能直接读取仿真特权状态”与“可以看到开发集结果”同时成立。预算和评测实现

可以把程序选择写成：

c∗=arg⁡max⁡c∈Csubmitted∑i=1Ndev1[Success⁡(c,Ei)]. c^*=\arg\max_{c\in\mathcal C_{\mathrm{submitted}}} \sum_{i=1}^{N_{\mathrm{dev}}} \mathbf 1[\operatorname{Success}(c,E_i)]. c∗=argc∈Csubmitted​max​i=1∑Ndev​​1[Success(c,Ei​)].

这里优化的是代码 ccc。Agent 根据反馈修改目标选择、动作顺序、阈值和恢复逻辑；测试阶段固定这些逻辑，检查它们能否适应新的场景。

冻结代码仍然可以闭环执行。 solve(bot) 可以读取当前图像，重新估计位置，根据运动反馈分支或重试。被冻结的是决策程序，不是整段关节轨迹。测试时“不再调用 LLM”，也不等于没有神经网络：分割、抓取等工具仍可能运行学习模型。

6. 它已经做到哪一种自我改进？

这里可以分成三个层次。

层次 改进的对象 当前应该怎样理解
任务解法改进 当前任务的程序、参数和动作逻辑 Auto Research 直接支持
技能积累 从多个任务抽取、保存、检索和组合通用技能 输出程序提供了基础，仍需跨任务实验
整个 Agent 系统改进 工具接口、工作流、记忆组织、模型调用策略 需要另外设计优化与评测机制

例如，Agent 发现侧面抓取容易撞到桌沿，于是换一个接近方向，这是任务解法改进。若它能从多个案例中抽取“靠近桌沿的物体怎样抓取”，以后遇到新物体时检索这条经验，才更接近技能积累。

程序验证器通过 AST 检查限制公开 API、导入和属性访问，有助于保持评测边界；源码也明确说明，这不是防范恶意 Python 的安全沙箱。对于研究结论，更重要的是确认最终程序没有读取测试答案，也没有把开发阶段的特定位置直接写死。程序验证实现

所以我会把它定位为：有明确开发预算和冻结测试阶段的程序化策略改进框架。 从这里进一步做技能库很自然，但“每个任务留下一份代码”还不足以证明能力能随任务数量持续增长。

7. Agentic Simulation：任务生成与任务求解分开

这一流程让 Builder 根据需求生成仿真任务、场景和示范，再让 Solver 为固定任务编写解法。它允许使用特权仿真信息，适合研究场景构建和程序求解，信息条件与 Agent as Policy 不同。Agentic Simulation 文档

这个分工的意义在于，生成任务和解决任务有不同目标。Builder 要把“搬运方块”落实成初始状态、动作接口、终止条件和成功判定；Solver 要在这些条件下找到行动程序。如果求解时还能任意改评分，任务就失去意义，因此任务冻结和完整性检查很重要。

源码实际检查了初始对象布局变化、无动作不能直接成功、初始姿态与简单的渲染条件，以及示范至少能解决一个种子。默认检查 8 个种子，Solver 要在步数预算内全部成功。Builder、示范与 Solver 可以接触同一组种子，因此这不能直接算作未见种子泛化实验。验收实现

工作流文档还规定复制冻结任务、排除示范文件，并做只读和指纹检查；本次确认了这项文档约定，未完整核实它在运行器中的实现。已读的验收代码会给 Solver 完整的环境对象，包装 env.step 来计步与判断终止，但这本身不能证明任意环境内部修改都已被阻止。

这些检查能发现一部分明显问题，但还有更难的质量问题：目标区域是不是过大，接触参数是否合理，成功是否来自评分漏洞，多个种子是否只改变无关细节。示范能成功，也只能说明任务存在一个可行解，不能证明任务覆盖了有价值的能力。

如果用它扩展机器人基准，我会先独立验收任务，再冻结任务集，最后比较求解 Agent。否则任务难度随生成器变化，模型成绩就难以解释。

8. Real2Sim：从视频重建到物理执行，中间还有几道关

Real2Sim 的流程可以理解为：

人手与物体交互的视频
  → 分割、深度与相机估计
  → 物体网格、人手姿态和运动轨迹
  → 尺度对齐、物体跟踪、碰撞几何
  → MuJoCo 场景与运动重放
  → 机器人手重定向、物理交互修正

公开工具包括 SAM 3、MoGe、GeoCalib、SAM 3D、HaWoR、CoACD、MuJoCo 与 Blender，分别服务于分割、几何恢复、重力方向、手部运动、碰撞分解和渲染等环节。项目还提供手部重定向与 SimMPC 相关流程，用来处理直接重放不能完成的物体交互。Real2Sim 文档

这里至少有三种不同的“对齐”。

第一是几何尺度对齐。视频估计出来的物体和手，需要处在统一尺度与坐标系里。外观相似但尺寸不对，机器人就会抓偏；利用手部尺寸等先验可以帮助恢复尺度，但这依然带有估计误差。

第二是人体与机器人运动学对齐。人手和 Sharpa 灵巧手的结构不同，直接复制关节角没有意义。可以用一个概念性目标说明重定向：

qt∗=arg⁡min⁡qt∑iwi∥pirobot(qt)−pihuman(t)∥2+λR(qt). q_t^*=\arg\min_{q_t} \sum_i w_i\left\|p_i^{\mathrm{robot}}(q_t) -p_i^{\mathrm{human}}(t)\right\|^2+\lambda R(q_t). qt∗​=argqt​min​i∑​wi​​pirobot​(qt​)−pihuman​(t)​2+λR(qt​).

它表达“尽量匹配关键点，同时满足机器人结构约束”的思路，不是源码损失的逐项复现。

第三是动力学对齐。手指经过正确的位置，仍可能因为摩擦、接触时机或受力方式不对而没抓住。引入物理仿真和反馈优化，才有机会修正这类问题。

发布介绍中的翻花绳很吸引人，但绳索还涉及形变、张力、滑动和拓扑变化。演示与工具链说明了一条可行的重建路线，尚不足以证明任意绳索操作都能稳定复现。更进一步，从视频获得仿真轨迹，到训练能适应新初始条件的策略，再到真机执行，也分别需要验证。

9. Motion Generation：动作看起来对，和机器人能执行，是两件事

Motion Generation 使用 Kimodo、GVHMR、WiLoR 等工具生成或恢复运动，再进行角色与机器人重定向，通过 Blender 渲染检查。Agent 可以根据任务选择工具，编写数据转换代码，再根据画面修正结果。Motion Generation 文档

它的主要输出是运动学动画。一个网球发球动作可能具有自然的身体姿态，但要让机器人真正完成，还需要检查支撑、平衡、关节速度、力矩和接触。

这也解释了它与 Real2Sim 的分工：Motion Generation 更侧重动作和画面；Real2Sim 将重建结果放入物理环境，进一步处理交互。两者都可以为机器人学习提供数据或参考，但不能直接把动画质量当成控制成功率。

发布介绍提到多人运动迁移，而 README 提供的固定 video-to-character 流水线面向单人的身体动作。更一般的多人任务需要 Agent 额外组织工具和处理数据，不能把演示范围当成默认流水线全部自动支持的范围。

10. Low-cost 的结果应该怎样看？

官方 README 展示了以下案例：

工作流与案例 报告结果 报告费用与比较
Agent as Policy：RoboDojo stack_blocks DeepSeek 与 Claude Code 都为 5/5 DeepSeek 为 $0.16，约为 Claude Code 的 7%
Auto Research：RoboDojo press_by_number 双方都为 3/3 DeepSeek 为 $0.14，约为 Claude Code 的 13%
Real2Sim：DexYCB 罐头物体案例 展示重建流程 $0.09，约为 Codex 的 11%
Motion Generation：网球发球 展示动作生成 页面显示 $0.00，并与 Claude Code 比较

这里修正附件中的一处对应关系：Real2Sim 的 $0.09 对比对象是 Codex。 $0.00 则只能按页面显示精度理解，不能推出全部模型、算力和运行成本为零。官方案例表

这些结果说明，在已有工具充分支持的案例上，较便宜的模型也可能完成任务。但 3 个或 5 个种子规模很小；两组都全成功，也不能说明它们在更广任务上的能力相同。

成功率还有一个容易漏掉的口径：Agent as Policy 将部分 LLM 调用失败记为 void，排除在成功率分母外，并建议重跑。官方另列的学习策略评测对设置失败采用不同计数方式。因此横向比较前应同时列出总启动数、有效完成数、成功数、void 数和重跑费用，不能只拿一个成功率比较。结果记录与评测说明

这不意味着表中的 5/5 一定排除了失败；它意味着需要查看对应运行记录，才能知道分母怎样形成。

成本也建议拆开记录：

Ctotal=CLLM+Ctools+Csimulation+Cretry+Csetup. C_{\mathrm{total}}= C_{\mathrm{LLM}}+C_{\mathrm{tools}}+C_{\mathrm{simulation}} +C_{\mathrm{retry}}+C_{\mathrm{setup}}. Ctotal​=CLLM​+Ctools​+Csimulation​+Cretry​+Csetup​.

这是建议的核算框架。模型调用费用低，不代表感知模型部署、仿真和人工准备都同样便宜。若要证明“工具设计降低了成本”，还应该固定模型做工具与流程消融，避免把模型价格差异全部归因于 RoboSkills。

11. 和 Metatron、VLA、机器人 Agent 研究怎样接起来？

Metatron 与 RoboSkills 有一个共同点：高层代码不需要直接解决每个关节的控制问题。但它们下面承接的能力不同。

路线 高层主要输出 下层主要承担
Metatron 稀疏运动目标、时序和状态切换 学到的全身协调与控制
RoboSkills 工具调用、几何目标和执行程序 感知、规划、仿真与动作执行
典型 VLA 动作或动作块 由训练得到的策略连接观测和动作

这几条路线可以组合。例如，把某个可靠的 VLA 或全身控制器封装成工具，Agent 负责选择技能和组织任务；但实际收益取决于接口是否能说明前提、结果和失败原因。仅返回一个“失败”，往往不足以让 Agent 做出有根据的修复。

对 Robot-Use Agent 的评测，我认为最值得保留三组拆分：

  • 同一工具、不同 Agent：看模型理解反馈、选择动作和调试代码的差异。
  • 同一 Agent、不同工具与说明：看几何能力、抓取能力和流程知识贡献多少。
  • 同一程序、不同场景：看它是否真的利用观测，能否应对布局变化与执行误差。

灵巧接触任务还要补上更具体的失败分类：没定位到目标、抓取位姿不合适、规划不可达、接触后滑落、动作成功但任务状态判断错误。这样才能知道下一步应该改感知、规划、执行控制，还是 Agent 的决策逻辑。

12. 我最想沿着它继续做什么？

我最感兴趣的是让 Auto Research 形成一套能够跨任务使用的技能库。

现在一个清楚的起点是：任务进入，Agent 做实验，最后产出 solution.py。下一步可以要求 Agent 从成功与失败中抽取一个带适用条件的技能，例如“抓取靠近桌沿的小物体”，并附上需要的观测、动作参数、成功检查和常见失败。

然后在新任务上比较三种设置：从头写程序、检索旧程序、检索并组合抽象技能。评价指标除了成功率，还应包括新任务的实验次数、模型费用、工具时间，以及遇到不同物体或机器人时还能保留多少收益。

要证明积累有效，关键是固定测试任务，观察随着历史任务增多，新任务是否真的更省实验、更可靠。若只是给每个旧任务保存一个独立脚本，库虽然变大，能力未必增长。

RoboSkills 提供了一个很具体的研究起点：把机器人能力变成可调用的工具，把改进对象变成可检查的程序，把开发反馈和最终测试分开。 后续最有价值的问题，是这些程序怎样从一次性解法变成可迁移的经验，以及如何通过独立评测证明这种迁移发生了。
